# ADR-0003. Где хранить вложения пользователей

**Статус:** принято
**Дата:** 2026-10-20

## Контекст

Приложение TimeCapsule позволяет прикреплять к капсулам файлы (картинки, PDF). В ЛР2 и ЛР3 они лежали в папке `storage/uploads` на диске сервера приложения (том EBS). Пока сервер один, это работает, но такой сервер нельзя заменить новым или запустить рядом второй: файлы пользователей есть только на нём. Нужно выбрать, где хранить вложения, чтобы сервер приложения перестал хранить состояние и его можно было свободно заменять и масштабировать.

## Решение

Хранить вложения в бакете Amazon S3 (`timecapsule-dev-uploads-<nickname>`, префикс `uploads/`). Бакет закрыт от публичного доступа, с версионированием, правилом жизненного цикла и политикой «только HTTPS». Приложение получает доступ через роль сервера (IAM-роль с политикой `timecapsule-dev-app-s3`, без ключей в коде), а браузер скачивает файлы напрямую из S3 по подписанным URL.

## Рассмотренные альтернативы

### 1. Диск EBS сервера приложения (как в ЛР2/ЛР3)
Файлы на локальном диске сервера.
**Минусы:** файлы привязаны к одному серверу; его нельзя заменить или продублировать без потери или ручного переноса данных; диск надо отдельно бэкапить; ёмкость ограничена размером тома. **Отклонено.**

### 2. Общая файловая система Amazon EFS
Сетевая файловая система, которую можно примонтировать сразу к нескольким серверам.
**Плюсы:** несколько серверов видят одни и те же файлы; код работает с привычными путями на диске, менять модуль хранения почти не надо.
**Минусы:** дороже S3 за гигабайт; это файловая система, а не объектное хранилище — нет версионирования объектов, правил жизненного цикла и подписанных URL из коробки; файлы всё равно отдаёт сервер (грузит его трафиком), а не скачиваются напрямую клиентом. Избыточно для «положить и отдать файл». **Отклонено.**

### 3. Бакет Amazon S3 (выбран)
Объектное хранилище вне серверов.
**Плюсы:** файлы не привязаны к серверу — его можно заменить или масштабировать без потери данных; дёшево; встроены версионирование, правила жизненного цикла, подписанные URL; браузер скачивает файлы напрямую из S3, разгружая сервер; доступ ограничивается политикой IAM вплоть до одного префикса. **Выбрано.**

## Последствия

**Как пользователь получает файл и что ограничивает срок ссылки.** Приложение проверяет права пользователя на капсулу, затем создаёт подписанный URL на 5 минут и редиректит браузер на него — файл скачивается прямо из S3. Срок ограничен значением expiry при подписи (5 минут): по истечении S3 отвечает «Request has expired». Подпись привязана к конкретному ключу, поэтому поменять файл в ссылке нельзя.

**Что защищает от случайного удаления и что ограничивает рост стоимости.** От случайного удаления защищает версионирование: удаление ставит delete marker, а прежняя версия остаётся и восстановима; политика приложения не даёт удалять версии (нет `DeleteObjectVersion`). Рост стоимости ограничивает правило жизненного цикла: старые версии переходят в Standard-IA через 30 дней и удаляются через 90 (кроме 2 последних), а незавершённые multipart-загрузки чистятся через 7 дней.

**Что изменится при нескольких серверах и балансировщике.** Почти ничего: файлы уже не на серверах, а в общем S3, поэтому любой из нескольких app-server за балансировщиком отдаёт одни и те же вложения. Каждый сервер получает доступ через свою роль с той же политикой. Именно вынос файлов в S3 (и базы на отдельный db-server в ЛР3) делает серверы приложения взаимозаменяемыми и готовыми к горизонтальному масштабированию.
