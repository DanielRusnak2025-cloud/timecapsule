# ADR-0001. Способ доставки кода на сервер

**Статус:** принято
**Дата:** 2026-10-03

## Контекст

Приложение TimeCapsule развёрнуто на одном экземпляре Amazon EC2 (Amazon Linux 2023, регион eu-north-1) со связкой nginx + PHP-FPM + PostgreSQL. Код приложения хранится в публичном репозитории GitHub в организации `DanielRusnak2025-cloud/timecapsule`.

Нужно выбрать способ доставки новых версий кода на сервер. Требования: процесс должен быть повторяемым, предсказуемым, не терять файлы при выкладке и давать возможность вернуться к рабочей версии при ошибке. Специальность — Informatică aplicată, что допускает ручной способ, но хочется заложить основу для будущей автоматизации (CI/CD).

## Решение

Единственный источник кода — репозиторий GitHub. Сервер забирает код сам командой `git pull`, а не получает его копированием с машины разработчика. Шаги выкладки (`git pull` → `composer install` → `php bin/init-db.php` → перезапуск PHP-FPM) записаны в скрипт `deploy.sh`, который можно запустить одной командой, в том числе удалённо через `ssh <сервер> ./deploy.sh`.

## Рассмотренные альтернативы

### 1. Копирование файлов через scp
Файлы вручную копируются с компьютера на сервер командой `scp`.
**Минусы:** непонятно, какая версия кода сейчас на сервере; легко забыть скопировать файл и сломать сайт; откат к прошлой версии делается «как-нибудь»; код живёт на ноутбуке разработчика, а не в общем месте. Подходит только для пары статических файлов, не для полноценного приложения. **Отклонено.**

### 2. git pull вручную на сервере
Разработчик заходит на сервер по SSH и вводит по очереди `git pull`, `composer install`, `php bin/init-db.php`, перезапуск PHP-FPM.
**Плюсы:** источник кода — репозиторий, версия на сервере понятна (по коммиту), откат делается через репозиторий. **Минусы:** одни и те же команды набираются руками каждый раз, легко пропустить шаг (например, забыть `composer install` после обновления библиотек). Это рабочий, но не самый надёжный вариант.

### 3. Скрипт deploy.sh (выбран)
Те же шаги, но записаны в скрипт с `set -euo pipefail` (остановка при первой ошибке) и `git pull --ff-only` (защита от конфликтов с ручными правками на сервере).
**Плюсы:** ни один шаг не теряется, последовательность всегда одинаковая, запуск одной командой — локально или удалённо через SSH. По сути это простейший прообраз CI/CD. **Выбрано.**

## Последствия

**Плюсы:**
- Репозиторий — единственный источник правды; на сервере всегда известно, какой коммит работает.
- Выкладка повторяема и не зависит от памяти человека: все шаги в скрипте.
- Откат к рабочей версии делается через репозиторий (`git revert` + повторный деплой), история правок сохраняется.
- Запуск одной командой с компьютера (`ssh … ./deploy.sh`) — готовая основа для перехода на автоматический CI/CD.

**Минусы / риски:**
- Во время `git pull` файлы заменяются по одному несколько секунд — есть короткое окно, когда посетитель может поймать «половинчатую» версию.
- Нет автоматической проверки кода до выкладки: синтаксическая ошибка доедет до сервера и уронит сайт (ошибка 500), пока её не откатят вручную.
- Проверка `/health` подтверждает только работу PHP и базы, но не то, что страницы реально отрисовываются, поэтому поломка вёрстки мониторингом не ловится.

**Что улучшить дальше:** добавить в скрипт проверку синтаксиса (`php -l`) и автотесты до выкладки, мониторинг реальных страниц (а не только `/health`), и автоматический откат при ошибке после деплоя.
