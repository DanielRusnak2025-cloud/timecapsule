# ADR-0002. Где размещать базу данных

**Статус:** принято
**Дата:** 2026-10-13

## Контекст

Приложение TimeCapsule состоит из сервера приложения (nginx + PHP-FPM) и базы данных PostgreSQL. В ЛР2 они жили на одном сервере в default VPC, где все подсети публичны. В ЛР3 построена собственная VPC с публичными и приватными подсетями, и нужно решить, где разместить базу данных, чтобы защитить данные пользователей от доступа из интернета, сохранив при этом доступ к базе для сервера приложения.

## Решение

Разместить базу данных на отдельном сервере (db-server) в **приватной** подсети (private-a), без публичного адреса и без маршрута в Internet Gateway. Доступ к порту 5432 открыт Security Group db-sg только для web-sg (сервера приложения), доступ по SSH — только через bastion. Обновления пакетов — через временный NAT Gateway. База получает имя `db.timecapsule.internal` через приватную зону Route 53.

## Рассмотренные альтернативы

### 1. База на одном сервере с приложением (как в ЛР2)
PostgreSQL на том же сервере, доступ по localhost.
**Плюсы:** просто, нет сетевых настроек, нет задержки сети.
**Минусы:** приложение и база делят ресурсы и судьбу одного сервера; его нельзя заменить или масштабировать, не трогая базу; взлом веб-части даёт прямой доступ к базе на той же машине; данные и код перемешаны. Не масштабируется. **Отклонено.**

### 2. База на отдельном сервере в публичной подсети
Отдельный db-server, но с публичным адресом.
**Плюсы:** база отделена от приложения, может обновляться и масштабироваться независимо.
**Минусы:** публичный адрес означает, что порт базы потенциально достижим из интернета; защита держится только на Security Group и пароле — один неверный параметр открывает базу всему миру. Для хранилища персональных данных это лишний риск. **Отклонено.**

### 3. База на отдельном сервере в приватной подсети (выбрано)
Отдельный db-server без публичного адреса, в приватной подсети.
**Плюсы:** база отделена от приложения (независимая замена и масштабирование) и при этом недостижима из интернета — нет ни публичного адреса, ни маршрута наружу; доступ только изнутри VPC и только от веб-сервера (db-sg ← web-sg). Защита в несколько слоёв: сеть, Security Group, pg_hba.conf и пароль. **Выбрано.**

## Последствия

**Как база получает обновления без постоянного выхода в интернет и сколько это стоит.** У приватной подсети нет постоянного маршрута наружу, поэтому для установки обновлений безопасности создаётся **временный NAT Gateway** в публичной подсети (маршрут 0.0.0.0/0 → NAT в private-rt), а сразу после — удаляется. Постоянный NAT стоил бы ~$1,25/сутки круглосуточно; временный — центы за время установки. NAT пропускает только исходящие соединения, входящие извне остаются закрытыми.

**Почему у app-server Elastic IP и что изменится с балансировщиком.** app-server — публичная точка входа, его адрес не должен меняться при остановке/запуске, поэтому за ним закреплён Elastic IP (на нём завязаны APP_URL и обращения пользователей). Когда перед приложением появится балансировщик нагрузки, постоянным публичным адресом станет он: app-server уйдут в приватные подсети без собственных публичных адресов, и Elastic IP на сервере станет не нужен. База остаётся в приватной подсети при любом из этих вариантов.
